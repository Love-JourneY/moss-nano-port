# moss-nano-port 两端一致性(黑仔 ↔ 格仔 / chroot ↔ Android 引擎)

> ⚠️ **本文件的网络地址已匿名化**(2026-09-28 开源准备):
> 原文里是具体 IP,现替换为 `<平板IP>` / `<宿主IP>` 等占位符。
> 逻辑与结论【一字未改】—— 只动地址。

> **2026-09-24** · 本文回答一个问题:**同一套 moss-nano-port,在笔记本(chroot)与平板(Android 进程内)上,
> 行为一致吗?哪里必须一致、哪里允许不同、依据是什么。**

## 一、结论速览

| 维度 | 黑仔(笔记本 · chroot) | 格仔(平板 · Android 进程内) | 一致? |
|---|---|---|---|
| **模型** | moss-nano-port(MOSS-TTS-Nano 微调) | **同一份权重** | ✅ |
| **推理框架** | onnxruntime(pip) | `onnxruntime-android` 1.30.0 | ✅ 同源 |
| **推理图** | 4 个(prefill/decode_step/local_fixed_sampled_frame/codec decode) | **同一 4 个** | ✅ |
| **采样逻辑** | 烘在图里(audio 0.8 / top_p 0.95 / top_k 25 / rep 1.2) | **同一张图** | ✅ |
| **文本→音素** | `canto_hk_g2p`(Python 绑定) | **同一个 Rust 库交叉编译** | ✅ |
| **音节→token** | sentencepiece + added_tokens | **音节查表(实测逐位一致)** | ✅ 等价 |
| **普→粤** | `/usr/local/bin/p2y` | **同一份规则表 + Java 复刻** | ✅ 逐字节一致 |
| **切段** | `vsay-canto`(bash) | `CantoSegmenter`(Java) | ✅ 三档行为一致 |
| **音色** | `voicebank/*.json` | **同一批 json** | ✅ |
| **播放链路** | PulseAudio/paplay | TextToSpeechService callback | ⚠️ **允许不同**(平台机制) |
| **线程数** | 建议 4 | **建议 2** | ⚠️ **允许不同**(实测结论相反) |

**判据:凡"影响音频内容"的必须一致;凡"平台机制"的允许不同,但必须记下原因。**

## 二、必须一致的四件(以及怎么证)

### ① 推理数值一致 —— 逐样本比对过
```
Android vs 本机 Python 参照:
  帧数 33==33 · 随机数 578==578 · 样本数 126720==126720(文件字节数完全相同)
  最大绝对差 1(int16 满量程 32767)· 相同样本 99.85% · 相关系数 0.9999999999
  客观指标(时长 / F0 150.9Hz / RMS / 有声帧 84.6%)逐项完全相同
⇒ 残余 ±1 LSB 是 numpy np.round(四舍六入五成双)vs Java Math.round(四舍五入)
```
**⚠️ 但注意(2026-09-24 发现)**:上述一致是**在我们主动喂同一串随机数**时成立的。
生产环境的输出**天然不确定** —— 见 §四。

### ② 音节→token 一致 —— 逐位比对过
```
Python `_PhonemeEncoder` 输出:
  [8802, 10385, 307, 319, 10752, 271, 274, 10385, 5610, 10386, 1823, 10384, 672, 10384]
Java `CantoTokenTable` 输出:
  [8802, 10385, 307, 319, 10752, 271, 274, 10385, 5610, 10386, 1823, 10384, 672, 10384]
⇒ 【完全相同】
```

### ③ 普→粤一致 —— 逐字节比对过(14/14)
```
谢了,这个功能已经完成了。 → 多謝，呢個功能已经搞掂喇。
但是太貴了。               → 但係太貴喇。
我在等你。                 → 我喺度等你。
这个东西3元。              → 呢個嘢3蚊。
受不了。                   → 頂唔順。
我走了。                   → 我走喇。
...
⇒ 14/14 逐字节相同
```

### ④ p2y 在【引擎内】生效 —— 已验证
```
p2y 开:G2P 收到「我喺度等你，多謝。呢個嘢3蚊。」  ✅ 9/9
p2y 关:G2P 收到「我在等你,谢了。这个东西3元。」  ✅ 原样
⇒ 开关可切,且链路上位置正确(在切段之前、合成之前)
```

## 三、允许不同但要记原因的

### ① 播放链路:平台机制不同
| | 机制 | 为什么不能统一 |
|---|---|---|
| 黑仔 | `vsay-canto` → paplay / PulseAudio | Linux 桌面音频栈 |
| 格仔(旧) | chroot 合成 → `SpeakTriggerActivity` 播(⚠️ 只吃**一个** wav ⇒ 必须先拼接) | 平板 chroot 里没有 PulseAudio 守护;`aplay` EINVAL(`ohalservice.qti` 占着 `/dev/snd`) |
| 格仔(新) | `TextToSpeechService` 的 `callback.audioAvailable` | **系统 TTS 框架规定**的接口 |

**⚠️ 踩过的坑**:`callback.maxBufferSize` **单位是字节不是采样点**。
当采样点用 ⇒ `ByteArray(n*2)` 是上限的两倍 ⇒ `audioAvailable` 抛异常
⇒ 表现**绑定成功、语言对、speak() 返回 SUCCESS、合成也成功,但永远静音**。

### ② 线程数:实测结论相反
```
Android(bionic ORT, 8 核)   loop
  threads=1 2026ms | 2 2368ms | 4 2706ms | 8 4686ms
⇒ 【1~2 最快】;而 chroot/glibc 时代记的是"4 最优"
⚠️ 1/2/4 的输出 md5 完全相同 ⇒ 线程数不影响数值,只影响速度
⇒ 所以"允许不同"不影响一致性
```

## 四、🔴 一条必须知道的事实:输出天然不确定

```
同一段文本连打 3 次 /speak-audio:音频 7.52s / 7.12s / 9.76s(差 37%)

根因:should_continue 是【图内由文本侧采样结果推出来的】,
     而文本侧采样吃【我们喂的 u】⇒ 【终止条件本身是随机的】
     ⇒ 同一句话的音频时长【天生会波动】

⇒ 工程对策:
  · Android 引擎【默认固定 seed】(DEFAULT_SEED=20260923L)⇒ 可预测延迟与时长
    要多样性时调 setSeed()
  · 黑仔侧保持每次不同(人听感更自然)
  ⚠️ 这【不算两端不一致】—— 是"随机性"这件事本身在两个实现里都真实存在
⇒ 评测纪律:单次对比不可靠,要【多次采样取统计量】
```

## 五、DSH 🔊 插件两条路的一致性

| 路 | 走向 | 状态 |
|---|---|---|
| `/speak`(本机) | DSH GUI → `dsh-tts` server → `vsay` → 黑仔扬声器 | ✅ |
| `/speak-audio`(远端) | DSH GUI(平板浏览器)→ **黑仔** `:8790` → 合成 → 回传 wav | ✅ 实测 200 + 有效 WAV |

**⚠️ 关键事实(2026-09-24 日志实证)**:
```
平板浏览器打到的是【黑仔的 :8790】:
  origin=http://<宿主IP-备用>:3081  ttsBase=http://<宿主IP-备用>:8790  isLocal=false
⇒ 【平板不跑自己的 dsh-tts server.js】
⇒ 所以"不切分"策略只在 server.js 里改一次,【两端自动一致】(md5 冻结未破)
```

**⇒ 这条与 Android 引擎的关系**:
- **现在的**平板播放:走 DSH 插件远端路(合成在黑仔)
- **未来的**平板播放:可以是**系统 TTS 引擎**(合成在平板进程内)
- **两者不冲突** —— 前者是"网页里点 🔊",后者是"任意 App 调系统 TTS"
- **⚠️ 引擎内的 p2y/切段/音色 必须与黑仔一致**(见 §二),否则同一个 🔊 按钮在两条路上念得不一样

## 六、变更涟漪:改一处要扫哪些面

| 改了 | 必须同步/检查 |
|---|---|
| `p2y-rules.tsv` | 重跑**逐字节比对**(Java vs Python);改 `/usr/local/bin/p2y` 时**两边一起导表** |
| `syllable-ids.tsv` | 重跑**逐位比对**(与 `_PhonemeEncoder` 对齐) |
| `voicebank/*.json` | 两端同步;**检查许可**(不得收 `vits_clean`) |
| 切段策略 | 黑仔在 `server.js`;Android 在 `CantoSegmenter` ⇒ **两边都要改** |
| 模型图 | 重跑**逐样本比对**;`CantoOrtEngine` 里的形状契约(n_vq/row_width/层数)要跟着核 |
| `install.sh` 推的路径 | 反向 grep:`CantoTtsService.resolveModelDir()` 与 `CantoG2pJni` 的路径要一致 |

**验收标准 = 反向 `grep` 零命中**(排除 `.bak` 与史册)。

## 输出采样率:两端统一 24kHz(2026-09-26 立)

**Nija 指示:**
> 「如果我们所有设备的TTS,全部把生成合成的音质稍微降一降。…我们可以砍一半,ok?
>  因为…很多音乐平台上那种无损音质和普通MP3音质,我都听不太出来区别。」

| 侧 | 实现 | 配置 |
|---|---|---|
| **笔记本** | `tts_stream.py` 的 `downsample_wav()` | 环境变量 `CANTO_OUTPUT_RATE`(默认 **24000**) |
| **Android** | `CantoResampler.java`(守护侧) | `tuning.properties` 的 `outputSampleRate`(默认 **24000**) |

**⚠️ 三条共同约束(两端都适用):**
1. **必须【先低通滤波再抽取】** —— 直接"每两个取一个"会混叠失真(高频折回,听起来发闷)
2. **降采样【不省推理时间/内存】** —— 模型内部就是 48kHz 生成的;只省传输/缓冲/文件
3. **降采样失败【不许静默】** —— 打日志,保留原音频(Android 侧是 stderr → logcat)

**⚠️ 一个语义细节:笔记本侧的守护【在启动时读环境变量】**
⇒ 想改回 48kHz 必须【重启守护】(带 `CANTO_OUTPUT_RATE=48000` 起),不能只改客户端环境。
