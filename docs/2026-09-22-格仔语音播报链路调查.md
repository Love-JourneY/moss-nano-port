## 一、播放路径现状:`vsay-canto-female` 在平板上到底走哪条?

### 1.1 脚本真实内容(平板 `/usr/local/bin/vsay-canto-female`,937 行 Python)

播放函数在 **606–617 行**,原文:

```python
def play(path: Path) -> None:
    """播放:优先 paplay/PipeWire,退回 pw-play/aplay。失败不致命(可能只想要文件)。"""
    for cmd in (["paplay"], ["pw-play"], ["aplay", "-q"]):
        if shutil.which(cmd[0]):
            try:
                subprocess.run(cmd + [str(path)], check=True,
                               stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
                return
            except Exception:
                continue
    print("[warn] 没有可用的播放器,只生成了 wav", file=sys.stderr)
```

**关键判据:它只用 `shutil.which()` 判断"二进制在不在",从不判断"音频服务在不在"。**
对面(男声)`/usr/local/bin/vsay-canto` 是**已经修好的版本** —— 它加了服务探测:

```bash
_pa_ok()  { [ -n "${PULSE_SERVER:-}" ] || ls /run/user/*/pulse/native /run/pulse/native 2>/dev/null | grep -q . ; }
_pw_ok()  { [ -n "${PIPEWIRE_RUNTIME_DIR:-}${XDG_RUNTIME_DIR:-}" ] && ls "${PIPEWIRE_RUNTIME_DIR:-$XDG_RUNTIME_DIR}"/pipewire-0 2>/dev/null | grep -q . ; }
```
（脚本注释原文:「**光有二进制不算数** —— 平板 chroot 里装了 pw-play,却没有 PipeWire 守护 ⇒ 探测"通过"、播放必失败,还看不出为什么」）

**⇒ 女声脚本漏了这个修复,这就是它不出声的直接原因。**

`stderr=DEVNULL` + `except: continue` 把失败**吞掉了**,最后只留一句"没有可用的播放器"。

### 1.3 被吞掉的真实报错(手工复现,完整原文)

| 命令 | 完整输出 | 出口码 |
|---|---|---|
| `pw-play /tmp/pad-test/seg-01.wav` | `error: pw_context_connect() failed: Host is down` | 1 |
| `pw-cat -p …` | `error: pw_context_connect() failed: Host is down` | 1 |
| `pw-cli info 0` | `Error: "failed to connect: Host is down"` | — |

## 二、chroot 音频环境(全部第一手实测值)

| 项 | 实测值 |
|---|---|
| **有没有 PipeWire/Pulse 守护** | **没有**。`/proc/*/comm` 全表无 pipewire / pulseaudio / wireplumber |
| `paplay` / `pacat` / `pactl` / `pulseaudio` | **全缺** |
| `pw-play` / `pw-cat` / `pw-cli` / `pipewire` | **在**(`/usr/bin/…`,libpipewire 1.4.2) |
| `aplay` / `amixer` | 在(`/usr/bin/…`) |
| `/run/user/*/pipewire-0` | **不存在** |
| `/run/user/0/pulse/` | 目录**存在但为空**(没有 `native` socket) |
| `/run/pulse/native` | 不存在 |
| **`XDG_RUNTIME_DIR`** | **未设** |
| **`PIPEWIRE_RUNTIME_DIR`** | **未设** |
| **`PULSE_SERVER`** / `PULSE_RUNTIME_PATH` / `PIPEWIRE_REMOTE` | **全未设** |
| `TMPDIR` | `/data/local/tmp`(从 Android env 继承;chroot 里这个目录是**自己的**(inode 65098:313187),与 `/android/data/local/tmp`(65098:111)**不是同一个**) |
| `/etc/profile.d/` 里的音频注入 | **零**(只有 dsh-credentials / gnome-session / im-config / vte) |
| **`/dev/snd`** | **在**,44 个节点:`crw-rw---- 1000(system) 1005(audio)`,如 `controlC0`, `pcmC0D0p`…`pcmC0D38c` |
| `/proc/asound` | 可见,`card 0: sunmtpsndcard [sun-mtp-snd-card]`,`aplay -l` 列出 40+ 个 PCM |
| **chroot 与 Android 的音频 socket 是否同一个** | **是"都没有"** —— Android 侧本身不用 Pulse/PipeWire(走 audioserver + HIDL/AIDL HAL + `/dev/snd`),chroot 侧也没有服务端。两侧**不存在任何共享音频 socket** |
| **谁握着声卡** | `ohalservice.qti`(pid 13670)**持有 5 个 `/dev/snd/controlC0` fd**(root 实测 `ls -l /proc/13670/fd \| grep snd`);`audioserver`(13661)自己 0 个 ⇒ **独占者是 HAL** |

> `/mnt/bbSoyArch`(sshfs 只读挂到黑仔家目录)、`/mnt/android`(fuse → /sdcard)、`/android`(Android 根,erofs/f2fs bind) 都在 chroot 内可见 —— 这解释了 chroot 能读 Android 文件,但**读不到 Android 的音频栈**。

## 三、三条候选路径逐条结论

### A) 装 `pacat`(pipewire-pulse / pulseaudio-utils)—— ❌ 可行但**毫无用处**

| 问题 | 实测答案 |
|---|---|
| chroot 里能不能 apt 装? | **能**。`apt 3.0.3 (arm64)`;`pulseaudio-utils` 候选取得到(`17.0+dfsg1-2+b1`,源 `mirrors.tuna.tsinghua.edu.cn`);网络**通**(`deb.debian.org → 200`,`mirrors.tuna → 200`) |
| 要不要联网? | 要,但网是通的 |
| 离线包有没有? | 本地无缓存包(未做离线归档) |
| `pipewire-pulse` 装了吗? | **已经装了**(`1.4.2-1`)—— 但 `pacat/paplay/pactl` 属于 **pulseaudio-utils**,所以才缺 |
| 装完能连到哪个 pulse server? | **一个都没有**。chroot 无守护、Android 无守护、`/run/user/0/pulse/native` 空 ⇒ `pacat` 装完照样 `Connection refused` |

**⇒ 结论:不可行(确切说"装了也没用")。** 缺的不是客户端二进制,是**服务端**。
即便再进一步自己在 chroot 起 `pipewire`,它的 ALSA sink 还是要写 `/dev/snd` ⇒ 回到第 1.3 的 `Invalid argument`。

## 五、给上级 agent 的建议

1. **推荐路径:唯一可行 = B(`SpeakTriggerActivity --es wav_path`)。** A 与 C 已逐条实测否掉,不要再重复趟。
2. **需要用户批准的事**:在格仔上执行一次(或多次)`am start -n com.fcitx5sensevoice/.SpeakTriggerActivity --es wav_path <路径>`。
   - 它**不创建窗口**(`Theme.NoDisplay`,非透明),但**会短暂把 App 进程提到前台,并且真的会出声**;
   - 用户抱怨过的是「弹语音输入设置页」(`SettingsActivity`),**不是这个**;
   - 仍建议先打招呼("我现在让平板念一句粤语女声,不会弹界面,会出声")。
3. **长期修法(建议,未实施)**:把 `vsay-canto-female` 的 `play()` 补成跟男声 `vsay-canto` 一样的三段式——
   ① 先 `_pa_ok`/`_pw_ok` 判服务;② 判不到时**不静默吞错**,而是走"落盘 + 交给 App 播"这条路(脚本 902 行的注释其实**已经写明** `--out` 就是为 `SpeakTriggerActivity --es wav_path` 准备的)。
   **⇒ 现状是"设计意图已经写了,只差把 play() 接上"。**
4. **不要**去装 `pulseaudio-utils` / 不要在 chroot 起 PipeWire —— 白费,且增加熵。
5. 若必须"完全零 UI 且不碰 Activity",目前**没有可行解**;只能等 App 被自然唤起后蹭 `127.0.0.1:8791/play_wav`(**不可靠**,见 §3-C 第一行)。

## 六、仍存在的问题 / 未解项

1. **最后一跳未取证**:按指令未触发 Activity ⇒「女声经 App 出声」这句**本轮无法给出第一手 audio_flinger 证据**(男声那条早前已由前一轮 subagent 实测出声,不是本轮)。
2. **App 的本地 HTTP(8791)实际上已经坏死**:accept 循环退出后 `ensureStarted()` 不会重启它 ⇒ **同进程生命周期内 8791 再也接不了连接**,表现为 `Recv-Q` 越积越多。副作用:任何依赖 `127.0.0.1:8791` 的调用方(含黑仔上那条 `adb forward tcp:8791`)都会超时。**需要 App 侧小修(accept 失败要重试而不是 break)或重启进程。**
3. **`vsay-canto-female` 与 `vsay-canto` 行为不一致**:同一个坑,男声修了、女声没修(见 §1.1)。这是"同一能力两处实现"的典型漂移。
4. **`TMPDIR=/data/local/tmp` 被从 Android env 带进 chroot**:chroot 里恰好真有这个目录(自建,非 /android 的),所以没炸;但这是**隐式依赖**,一旦 chroot 重建就会变成"写不进去"。建议在 chroot 的 `/etc/profile.d/` 里显式设 `TMPDIR=/tmp`。
5. **本轮新增的临时物(未删,留证)**:App 共享目录里两个女声 wav —— `gezai-female-test.wav`(399404 B)、`gezai-3374384.wav`(568364 B);chroot `/tmp` 里无残留(合成脚本自清)。**没有删除任何既有文件。**
6. **`/run/user/0/gvfs` 挂载已断**(`Transport endpoint is not connected`)—— 与音频无关,但 chroot 桌面环境有残留 broken mount,顺手记一笔。
