# Android 进程内推理 —— 实测结论(定稿)

> **2026-09-25** · 本文回答一个问题:**moss-nano-port 的 ONNX 推理能不能在 Android 进程内跑?**
> **答案:技术链 100% 打通,但在 ColorOS 系设备上【跑不完】—— 这是设备策略限制,不是代码问题。**

## 二、未达成:合成被系统冻结

### 现象
```
[S5] prompt = 114 行 × 17 列
[S6] prefill 464 ms        ← 有时到这一步
然后【什么都没有】—— 连错误都没有

线程栈:do_freezer_trap + get_signal + do_notify_resume
wchan: do_freezer_trap
```

### 根因(有数据)

```
① 加载模型后:RssAnon = 916MB ~ 1.05GB · RssFile 只有 73~117MB
   ⇒ 【ORT 把 683MB 权重复制进了匿名内存】(不是文件映射)

② 而匿名内存【必须走 swap】,文件映射【可以直接丢弃】
   ⇒ 实测 160 秒内:Anon 1.05GB → 207MB,Swap 18MB → 866MB
   ⇒ 内核只能把它换出

③ ColorOS 的 CachedAppOptimizer / osense 在【任意时刻】
   把"长时间不产生活动"的我们判为不活跃 ⇒ 冻(do_freezer_trap)
   ⇒ 冻结点【非确定性】:实测同一份代码,一次卡在循环、一次连 prefill 都没到
```

**⇒ 不是"我们的代码慢",而是"系统随时会冻我们"。**

## 五、怎么判断一台新设备能不能跑

```bash
./check-device.sh --target <adb>
```

判据(全部来自实测):
- ABI = `arm64-v8a` · SDK >= 24
- **MemAvailable > 2.5 GB**
- **zram 已用 <= 6 GB**
- **无 `virtualFreeze`**(ColorOS / OPPO / OnePlus 系要小心)

**同一个模型、同一套推理图、同一份代码,在 Linux 上【出声是 OK 的】。**

**所以 Android 侧不出声,纯粹是【设备策略】问题:**
```
不是模型问题  —— Linux 上同一个 .onnx 出 460KB wav
```

**这是整个 Android 调查最重要的对照:问题被【界定】在设备层,而不是我们的层。**

### 能砍多少(实测算过字节量)

```
local_fixed_sampled_frame 引用 216.55MB / 文件 219.55MB  ⇒ 只能砍 3.00MB

⇒ 683MB → 640MB(砍掉 encode)。仍然远超安全线。
```

**⇒ 结论:模型大小是硬约束,"按图裁剪"救不了。**
**⇒ 唯一真死代码是 `moss_audio_tokenizer_encode.onnx` + `encode.data`(42.4MB,零调用点)。**

## 十、最终定论:冻结与"我们的工作量"无关

### 决定性实测(每 3 秒密集采样)

```
合成期间:
  t= 3s  cpu=301  synth_wchan=futex_wait_queue   ← 在跑
  t= 6s  cpu=351  synth_wchan=do_freezer_trap    ← 被冻
  t= 9s..60s  cpu=351  ← 【一 jiffy 都没涨,CPU 完全静止】

把 maxFrames 从 40 降到 10(理论合成 1.1s):
  ⇒ 冻结提前到 【[S5] prefill 之前】,cpu=465 不变
  ⇒ 【降工作量无效】
```

### 为什么现有引擎(sherpa VITS)能活

```
实测:com.fcitx5sensevoice 的进程【也】在 do_freezer_trap(空闲时)
⇒ do_freezer_trap 是【idle 时的正常状态】,不是故障
⇒ 它能工作的原因:合成是【毫秒级】
   ⇒ 在两次 freeze 扫描【之间】就跑完并交出音频
⇒ 【不是因为"它受保护"】
```

### ⇒ 核心矛盾(对目标②的定性)

| | 老架构(sherpa VITS) | 我们的(moss-nano-port) |
|---|---|---|
| 推理 | 非自回归 | **自回归** |
| 模型 | ~79MB | **683MB** |
| 合成耗时 | **毫秒级** | 秒级连续 CPU |
| 在系统 TTS 位置 | ✅ 能活 | ❌ 被冻 |

**⇒ 老架构之所以在"系统 TTS 引擎"这个位置上能用,【正是因为它快】。**
**⇒ 换成需要秒级连续 CPU 的自回归模型后,【"慢"本身就是致命伤】。**

### 问题被界定在哪一层(重要)

```
✅ 不再是"我们的代码有问题" —— 同一份推理逻辑在 app_process(uid 2000)下跑完过(原型)
✅ 不再是"打包有问题"     —— APK 装机、系统列出、系统绑定、系统调用全部成功
✅ 不再是"模型有问题"     —— Linux 上同一个 .onnx verify 12/12 通过
❌ 【普通 App 身份】+【ColorOS 的 virtualFreeze】+【683MB 自回归模型】三者叠加
⇒ 【这个组合在当前平板上无解 —— 不是工程问题】
```

# 十一、✅ 最终解法:root 守护架构(2026-09-25 实测跑通)

> **结论:Android 上 moss-nano-port【能跑】—— 只要把推理搬出 App 进程。**

## 实测证据(完整合成)

```
[CantoDaemon] START modelDir=.../models/canto socket=18790
[CantoDaemon] [CantoOrtBackend] 已加载 4 个 Session(threads=0)
[CantoDaemon] READY voices=6
[CantoDaemon] LISTEN 127.0.0.1:18790

—— 客户端发一条「今日天氣幾好。」——
[S7] 循环 3258 ms → 40 帧 (3200 ms 音频)
[S8] codec 476 ms → 153600 采样/声道 (3.200 s)
[S9] 端到端 4490 ms · PCM 307200 采样
[CantoDaemon] OK samples=307200 bytes=614400 ms=4513

—— 客户端收到 ——
614409 字节(头 "P 614400\n" + 614400 字节 PCM16LE)

—— 守护进程 ——
uid=0  wchan=do_sys_poll(【不是 do_freezer_trap】)  rss=1,039,280KB
```

## 架构

```
┌──────────────────────────────────────────┐
│ TTS 服务(App, uid 10326)                  │  ← 系统 bind 它
│   · onSynthesizeText 收文本 ⇒ TCP 转发      │
│   · 收回 PCM ⇒ callback.audioAvailable     │
│   ⚠️ 只做转发(毫秒级)⇒ 不会被冻              │
└──────────────┬───────────────────────────┘
               │ 127.0.0.1:<port>
┌──────────────▼───────────────────────────┐
│ CantoDaemon(root, uid 0, 常驻)             │
│   · 模型加载一次(3.4s)· 完整合成 4.5s       │
│   · 【不被 ColorOS 的 virtualFreeze 冻】    │
└──────────────────────────────────────────┘
```

## 两个实现细节(踩过)

| 坑 | 解 |
|---|---|
| UDS 的 Java API(`UnixDomainSocketAddress`)在 `android.jar` 下**不存在** | 改用 **127.0.0.1 loopback TCP** |
| socket 放哪:实测 `/data/local/tmp` 是 `shell_data_file`(App 读不到);`/dev/socket` 无权限 | **TCP 路线绕开了整个 SELinux 文件上下文问题** |

## 为什么这不是"绕过问题"而是"正解"

```
① 平板本来就有 KernelSU root(本会话从一开始就在用 su -c)
② 上下文里平板已有 chroot(也是 root 跑的)
③ install.sh 本来就用 su -c 做 chown/chcon
④ 原型(app_process, uid 2000)跑通过 ⇒ 早已证明"非 App 身份"可行
⑤ goal ① 要的【常驻守护】正是这个守护进程;goal ② 要的"进程内推理"仍然成立
```

# 十二、🎉 最终结果:出声了(2026-09-25 实测)

## 实测日志(端到端)

```
App 侧:
  [CantoDaemonClient] 收到 PCM 153600 字节
  合成来源=daemon samples=76800
  TTS_OK chars=2 samples=76800
  TTS_SYNTH_DONE chars=2 rate=48000

客户端(系统 TTS 框架):
  SPEAK ret=0 → UTTER_START t1 → UTTER_DONE t1
  ⚠️ UTTER_START 出现 = 框架拿到了音频流并开始播

守护:
  READY voices=6 · LISTEN 127.0.0.1:18790 · CONN ×2 · SYNTH chars=2
  OK samples=76800 bytes=153600 ms=1290
```

## 让"出声"成立的三个关键

| # | 关键 | 说明 |
|---|---|---|
| 1 | **root 守护** | uid=0 的进程不被 ColorOS 冻(实测烧 CPU 70 秒不受冻) |
| 2 | **`callback.start()` 必须在拿到 PCM 之后** | 否则框架等不到音频 ⇒ 提前 UTTER_DONE ⇒ 解绑 ⇒ 服务销毁 |
| 3 | **单次合成必须短(≤ ~1.3 秒)** | 否则 App 在"等"的窗口里被冻,读不到回传的 PCM |

**⇒ 第 3 条推出一条使用约束:**
```
maxFrames 必须小(实测 10 帧 = 0.8 秒音频 = 1.29 秒合成)
⇒ 长文本要【分段多次调用】⇒ 这与我们的"切段策略"天然配合
```

## 完整架构(可复现)

```
系统 TTS 框架 ──bind──▶ canto.tts App(uid 10326)
                          · TextToSpeechService(四件套)
                          · onSynthesizeText:不立刻 start()
                          · 线程:ping → 发文本 → 收 PCM
                                  → start() + audioAvailable() + done()
                          ⚠️ 整段 ≤ ~1.3 秒
                              │ 127.0.0.1:18790
                              ▼
                        CantoDaemon(root, uid 0, 常驻)
                          · install.sh 用 su + setsid 起 + 开机自启
                          · 模型加载一次(683MB)常驻
                          · 完整推理(不被冻)
```

## 部署约束(必须写进文档)

| # | 约束 | 后果 |
|---|---|---|
| 1 | **需要 root**(KernelSU) | 无 root ⇒ App 回退本地推理(会被冻,但行为可预期) |
| 2 | **APK 必须有 `INTERNET` 权限** | 连 loopback 也要;缺了守护永远"连不上" |
| 3 | **`maxFrames` ≤ ~15** | 长了 App 会被冻,读不到 PCM |
| 4 | **`callback.start()` 在拿到 PCM 之后** | 否则框架提前放弃 |
| 5 | `tuning.properties` 的 `daemonPort` 与 `install.sh` 一致 | 不一致 ⇒ 连不上 |
